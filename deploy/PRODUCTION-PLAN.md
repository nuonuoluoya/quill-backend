## 2. 代码、数据库、音频、密钥分开存放

| 内容 | 计划位置 | 更新规则 |
| --- | --- | --- |
| 新项目部署目录 | `/opt/quill-listening` | 与旧 `/home/quill-backend` 分离 |
| 各次代码与镜像版本 | `/opt/quill-listening/releases/<commit>`，镜像以提交号标识 | 发布新版本，保留上一可运行版本 |
| PostgreSQL 数据 | 固定名称的独立持久卷 `quill_pgdata` | 由数据库管理，应用发布不删除或重建 |

| PostgreSQL 初始化凭据 | `/etc/quill/postgres.env` | 独立受限配置，不与 API 共用管理账号 |

固定 Compose 项目名为 `quill-prod`，数据库卷采用固定外部卷，不因切换发布目录生成空卷。容器更换与数据卷生命周期独立，这是使用持久卷的目的，详见 [Docker 卷文档](https://docs.docker.com/engine/storage/volumes/)。音频目录权限应匹配 API 运行用户。

## 3. 阶段一：准备生产发布配置

先在本地按“规格 → 实现 → 验证 → 提交推送”的顺序完成：

1. 新增专用生产 Compose 配置。现有 `deploy/compose.yaml` 使用开发模式和演示口令，保留为本地联调示例。
2. API 设置 `NODE_ENV=production`；容器内监听 `0.0.0.0:3210`，仅映射服务器 `127.0.0.1:3210`。PostgreSQL 只允许内部网络访问，不发布宿主机公网端口。
3. 选择并锁定 PostgreSQL 版本与 Node 镜像版本。先按当前项目 Node.js 22.12+ 的要求验证，记录实际版本；不在发布过程中顺带升级数据库主版本。
4. 拆分一次性建表/迁移与常驻 API 启动，准备迁移身份和最小权限运行身份。已实现独立 `migrate.ts` 入口，生产 API 与普通 CLI 不再自动执行 DDL；部署时验证 API 无建表权限。
5. 配置容器正常停止时间，验证 API 收到停止信号后关闭数据库连接。配置健康检查、日志轮换，以及只信任已知反向代理的客户端 IP 处理，避免所有登录请求共用代理 IP 限流。
6. 运行类型、单元/集成、Schema、OpenAPI、构建检查，并增加真实 PostgreSQL 下的并发与权限验收。现有 PGlite 测试通过不等于已验证生产 PostgreSQL。

退出条件：生产发布文件可审查，镜像构建及上述检查通过。此时不切换服务器流量。

## 4. 阶段二：建立独立 PostgreSQL 和生产配置

1. 核对服务器资源、Docker/Compose 可用性、端口与目录冲突；实施时再执行必要安装，保留旧 MySQL 与旧应用。
2. 创建新项目目录、持久卷、音频目录与受限配置文件。初始化新的 PostgreSQL 数据库，只在新库执行本项目迁移。
3. 配置 API：

| 配置 | 生产取值要求 |
| --- | --- |
| `DATABASE_URL` | 新 PostgreSQL 的应用账号连接串，不连接 MySQL，不使用开发口令 |
| `PUBLIC_BASE_URL` | `https://codingluke.site`，不加 `/v1`，不加末尾斜线 |
| `MEDIA_ROOT` | `/app/media`，对应独立宿主机音频目录 |
| `WECHAT_APP_ID` / `WECHAT_APP_SECRET` | 与当前小程序一致，仅通过服务器秘密配置注入 |
| `MEDIA_SIGNING_SECRET` | 生产独立生成至少 32 字符，后续发布保持稳定 |
| `READY_TOKEN` | 独立生成，供受限就绪检查使用，不输出到日志 |
| `OPERATOR_CONTACT` | 有效的数据删除/运维联系方式 |

`DEV_DB_PATH` 不作为生产数据库路径；有 `DATABASE_URL` 时通过 PostgreSQL 连接池访问新库。日志不得包含连接密码、登录 code、访问 Token 或媒体签名查询串。

退出条件：新库迁移成功，运行账号权限符合要求，生产配置检查通过。

## 5. 阶段三：首次内容与本地数据入库

新建 PostgreSQL 不等于允许丢弃本地用户数据。执行本阶段前确认需保留的书籍、用户、授权、阅读进度及内容审计范围；默认迁入所有现有业务表，本地源数据保留，不清空或重置。

- **需要保留本地业务数据时**：制定并验证 PGlite 到 PostgreSQL 的逻辑导出/导入流程；不把 `.data/postgres` 目录作为 PostgreSQL 数据卷。处理主外键、活动构建引用、序列与数据类型，并核对迁移前后记录及媒体关系。已实现 `data:transfer` 导出、空库导入和摘要校验命令，需在实际目标 PostgreSQL 上核对。本地源数据保留；迁移临时产物与此前已取消的整套备份任务分开管理。
- **明确选择全新数据时**：新库按生产 CLI `validate → import → publish` 导入需要的原创/获授权书籍。生产环境禁止 `seed` 和 `dev-session`；不能把开发样本初始化命令直接搬到生产。
- 音频与书籍元数据同批验证，保留对象键和不可变构建身份，校验文件数量、字节数、哈希及引用。此前本地检查为 52 个媒体文件，这只是检查时的现状，执行时重新统计。
- 旧 MySQL 的笔记等历史数据不在本次迁移范围，不尝试按字段猜测映射到新项目。

退出条件：所需内容可查询、媒体引用完整、用户数据保留决定已落实；没有未经选择的数据丢失。

## 6. 阶段四：先在服务器本机验收新服务

启动新的 API，仅通过服务器回环地址测试：

- `GET /v1/health/live` 返回成功。
- 携带就绪检查凭据访问 `/v1/health/ready`，确认真实 PostgreSQL 查询成功；生产环境未带凭据返回 403 是预期行为。
- 覆盖书架、章节、公开样本、私有权限、进度读写与并发冲突。
- 覆盖媒体 GET/HEAD/Range、签名失效和越权拒绝，确认没有静态目录绕过媒体鉴权。
- 验证服务重启后数据库与音频不丢失。更换应用版本时禁止执行删除数据卷的命令。

退出条件：新服务本机验收通过，旧服务仍保留，尚未改变外部路由。

## 7. 阶段五：HTTPS 与域名接入

1. 重新核对 `codingluke.site` 的 DNS、证书及自动续期状态；修复过期证书，检查证书链和续期机制。
2. 复核现有 Nginx 路由。此前旧配置为 `location /` 代理到 `http://127.0.0.1:3000/api/`，不能将这个路径改写方式套到新 API。
3. 在同一域名增加 `/v1/` 与 `/media/` 的新服务代理，目标为 `http://127.0.0.1:3210`，保留原始路径及查询参数。代理地址不带 URI 时的路径保留行为见 [NGINX proxy_pass 文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)。
4. 先核对这两个路径未被旧业务使用，再执行 `nginx -t` 和配置重载；新服务公开验收通过后，按用户授权停止并删除旧应用目录、旧项目归档和对应 PM2 项目，移除旧代理路由；保留 MySQL。
5. 不为媒体目录增加公开静态映射，不启用绕过鉴权的代理缓存；访问日志使用不包含签名查询参数的格式。

退出条件：通过公开 HTTPS 地址访问新 API 和签名媒体成功，旧路径无意外变化，证书有效。失败则撤回新增路径配置，保留新 PostgreSQL 和音频数据。

## 8. 阶段六：小程序联调与完成确认

1. 将小程序生产 API 基址设为 `https://codingluke.site/v1`，按前端协作约定另行更新规格快照、检查、提交推送。
2. 在微信平台配置实际使用的 HTTPS 请求/媒体域名，核对发布条件；不能把开发者工具“不校验合法域名”当作上线验收。
3. 使用新的 `wx.login` code 完成真实登录；验证书架、章节、逐句播放、全文播放、倍速、进度同步及重新登录恢复。
4. 至少进行 iOS/Android 真机验证，记录构建版本、PostgreSQL 版本、上线时间和未通过项。

所有阶段完成后才报告已部署。仅文档完成、容器启动或无效登录 code 返回 400，都不足以证明真实登录和生产环境验收完成。

## 9. 后续更新与运维边界

后续更新只替换 API 镜像/代码并执行审查过的兼容迁移，持续复用 PostgreSQL 卷与音频目录。代码回退不执行数据库清空、音频删除或无条件恢复旧数据；启用新服务后已有新写入时，不能把切回旧系统视为自动完成数据回退。

新 PostgreSQL 的定期备份与恢复演练作为后续运维事项单独安排，不恢复此前取消的备份步骤，不在本次创建备份或自动化任务。采用逻辑备份时按 [PostgreSQL SQL Dump 文档](https://www.postgresql.org/docs/current/backup-dump.html) 选择匹配版本工具并验证恢复；当前尚未配置或执行。
